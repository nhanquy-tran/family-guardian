# Design

1. **Detection in SQL, sending in the endpoint.** ADR 0010 has cron "find" devices; here cron only triggers and the endpoint calls `find_offline_devices(p_now)` (`last_seen_at <= now - 15 min`, `>= now - 24 h`, no alert with `incident_last_seen_at = last_seen_at`). One tested source of truth, and no device ids travel in the request. The cron request body is empty.
2. **Claim before send.** Per device: insert the alert row, ignoring conflicts. If no row was inserted, skip (another run owns it). If `store.hasRecentEmail(device, now - 24 h)` is true, claim with `emailed_at` null and send nothing (banner only, counted as `throttled`). Otherwise claim with `emailed_at = now` and send the e-mails. If there was at least one recipient and every send failed, delete the claim so the next run retries; if at least one succeeded, keep it. Zero recipients: keep the claim, send nothing, log.
3. **Handler seams.** `handleOfflineAlerts({ authorization, secret, mailConfigured, now, store, mailer, log })` with `OfflineAlertStore` (`findOfflineDevices`, `hasRecentEmail`, `claimAlert(device, lastSeen, emailedAt | null)`, `releaseAlert`, `listParentEmails`) and `Mailer.send`. The Supabase store lives in `lib/alerts/supabase-store.ts` using `createAdminClient`; parent e-mails come from `auth.admin.getUserById` for the family's `parents` rows.
4. **Auth.** `crypto.timingSafeEqual` over SHA-256 digests of both values. Missing or empty `ALERT_CRON_SECRET` gives `500` and nothing is accepted. Wrong or missing header gives `401` with no DB call. Missing `RESEND_API_KEY` or `ALERT_FROM_EMAIL` gives `500` before any claim.
5. **Mailer.** `POST https://api.resend.com/emails`, bearer key, `text` body only; subject `"<child>: laptop offline"`; the body ends with "This is normal if the laptop was switched off. If it should be on, check the browser." Non-2xx or a thrown error is a failed recipient. Logs hold counts only, never addresses, names or ids.
6. **Cron.** `call_offline_alerts()` (security definer, not executable by API roles) reads `app_url` and `alert_cron_secret` from `vault.decrypted_secrets` and calls `net.http_post` with `timeout_milliseconds := 10000`. If either is missing it raises a warning and does nothing (tested on PGlite with stub `vault.decrypted_secrets` and `net.http_post`). `cron.schedule('offline-alerts', '*/5 * * * *', ...)`, `cron.schedule('purge-pair-attempts', '17 3 * * *', 'select public.purge_pair_attempts()')` (ADR 0012) and `create extension` for `pg_cron`/`pg_net` are guarded so the PGlite harness still loads the migration. Rotating the secret means updating the Vault entry and the Vercel env together; only one value works at a time.
7. **Banner.** `activeOfflineAlerts(rows)` (pure, `lib/alerts/banner.ts`) keeps rows where the device's `last_seen_at` equals `incident_last_seen_at`. `OfflineBanner` is a server component in the dashboard layout that reads `alerts` with the RLS client (existing `alerts_select` policy). Text: "<child>'s <browser> on <OS> has not reported since <time>".
8. **Verification gap.** PGlite has no `pg_cron` or `pg_net`; the two cron jobs and the Vault wiring are checked by hand on production after merge (see factory-learnings on migrations).
9. **Why throttle.** A switched-off laptop looks like a removed extension, so one e-mail per incident would reach parents every evening. E-mails are limited to one per device per rolling 24 h; the banner still shows every incident. A released claim leaves no `emailed_at`, so a failed send does not start the throttle.
10. **Known limits (MVP).** If the function times out between claim and send, that incident's e-mail is lost. If one of two parents' sends fails, that parent is not retried.
