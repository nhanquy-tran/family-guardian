# Design

1. **Schema** (new migration named at build time with `date -u`, newer than every migration on main; read existing ones first): `alter table public.families add column weekly_report_enabled boolean not null default false` and `grant update (weekly_report_enabled) on public.families to authenticated` (the `families_update` RLS policy limits the row; do not widen other columns). `usage_total_seconds(p_child_ids uuid[], p_start timestamptz, p_end timestamptz) returns table (child_id uuid, seconds bigint)`: `security definer`, `set search_path = ''`, execute revoked from `public, anon, authenticated`, granted to `service_role`; sums `usage_minutes.seconds` joined to `devices` by `child_id`, `minute_utc >= p_start and < p_end`, one row per child with usage. No new table: the claim is a `digest_runs` row with `frequency = 'weekly_report'` (that column has no check constraint; the key is `(family_id, frequency, period_start)`; the existing 90-day purge covers it). Known test risk: `supabase/tests/data-retention.test.ts` asserts that its migration is the last file; a human-owned test (see NOTES of #58), the test writer must flag it, not weaken it silently.
2. **Schedule**: `reportPeriod(family, now)` in `lib/digest/schedule.ts` calls `latestDuePeriod({ ...family, frequency: "weekly" }, now)` and returns it with `frequency: "weekly_report"`, plus the previous week's `start` (`prevStart`). `null` when the family was created after the send moment. Only the latest week is considered. The week start, week end and previous-week start are each computed as local Monday 00:00 in the family timezone (via `localToInstantMs`), never as `start - 7 days`, so a daylight saving change inside or between the weeks gives 167, 168 or 169 hour weeks.
3. **Content** (`lib/digest/weekly-report.ts`): `buildWeeklyReport({ familyId, timezone, period, appUrl, source, totals })` returns `{ subject, text, html }`. `source` is the existing `DigestSource` (`listChildren`, `readUsage` with the same paging and 30-page cap; a read error or going over the cap is `Usage unavailable` for that child only). `totals(childIds, start, end)` wraps `usage_total_seconds`; the current week is read as minute rows (`readUsage`) because the focus score needs them, capped at 30 pages; the previous week only needs a total, so it is aggregated in SQL; a failure for the previous week shows the change as "not available" and keeps the rest. Per child: total seconds; top 5 domains by seconds (ties by name); top 5 categories by seconds via `categorize` from `@fg/shared`; average focus score = mean of the daily `computeFocusScore` scores (days split in the family timezone, days with a null score skipped, rounded to an integer; none, or no homework settings: "Focus score not available"); change versus the week before as a signed percentage and minutes ("+25% (+2 h 00 min)"), or "no activity the week before" if that total is 0. No activity in the week: only "No activity this week". Durations use the digest's format.
4. **Rendering**: a minimal HTML document (`lang`, one `h1`, an `h2` per child, tables with `<th scope>` for categories and domains, no `<img>`, no `<script>`, no `<link>`, only the dashboard link `APP_URL/dashboard`). All names and domains are HTML-escaped. The text part carries the same content. Subject `Family Guardian: weekly report <first day> to <last day>`.
5. **Mailer**: the message type gets an optional `html`; `createResendMailer` forwards `html` only when present (the digest keeps sending text only).
6. **Delivery** (`handleWeeklyReportSend` in `lib/digest/weekly-report-send.ts`): same input shape as `handleDigestSend`, with a store method `listReportFamilies` (families with `weekly_report_enabled`) and a `build` callback returning `{ subject, text, html }`. Auth and configuration checks are those of the digest (digest-emails), re-applied here. Same claim/release rules and as the digest (reuses `claimDigest`, `releaseDigest`, `listParentEmails`). Opting in midweek sends a catch-up report for the previous week at the next Monday send moment (accepted, documented in the settings note).
7. **Route**: `POST /api/digest/send` runs `handleDigestSend` first; if it did not answer 200 that response is returned; otherwise `handleWeeklyReportSend` runs and its counts are logged (`weekly-report sent=.. skipped=.. failed=..`). The response body stays the digest counts. The route exports `maxDuration` (set at build time to cover the digest and the report running back to back) so the function is not cut short; the 10 s pg_net timeout on the caller only bounds the cron request, not the function. A report failure never changes the digest response.
8. **Settings**: `saveWeeklyReportSetting(client, enabled)` in `lib/digest/settings.ts` accepts only a boolean, updates the caller's family with `.select("id")` (error or zero rows is `failed`) and touches no other column. `loadWeeklyReportSetting(client)` reads `weekly_report_enabled` in a separate query from the digest select; on error the page shows an error message instead of defaults. `WeeklyReportForm` (`components/weekly-report-form.tsx`) shows a labelled checkbox "Weekly report", a note that all parents receive it on Monday at the digest hour, and a Save button; the settings page adds it below the digest form with a server action.
9. **Known limits**: a report lost to a function timeout between claim and send is not retried; if one of two parents' sends fails that parent is not retried; a family on a weekly digest also gets the digest on Monday (separate e-mails); the extra report work runs in the same call as the digest, so a slow run risks the function timeout (see `maxDuration`).
