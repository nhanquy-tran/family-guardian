# Design

1. **Schema** (migration named at build time with `date -u`; read existing migrations first): `families` gets `timezone text not null default 'UTC'`, `timezone_known boolean not null default false`, `digest_frequency text not null default 'daily'` check in (`daily`, `weekly`), `digest_hour smallint not null default 8` check 0 to 23. Grant `update (timezone, timezone_known, digest_frequency, digest_hour) on public.families to authenticated`; the existing `families_update` RLS policy limits it to the parent's family (check current grants first; do not widen `name`). `digest_runs(family_id fk on delete cascade, frequency, period_start date, claimed_at default now(), primary key (family_id, frequency, period_start))`: RLS on, no policy, all rights revoked from `anon` and `authenticated`. `alerts.resolved_at timestamptz` null. `purge_digest_runs()` deletes rows older than 90 days (security definer, empty search_path, execute revoked) and is scheduled daily next to `purge-pair-attempts`.
2. **Resolving incidents.** `resolve_offline_alerts(p_now)` (service role only) sets `resolved_at = p_now` on offline alerts with null `resolved_at` whose device `last_seen_at > incident_last_seen_at`. The offline handler calls it each run, so "to" is accurate to the 5-minute job. `OfflineAlertStore` loses `hasRecentEmail`, `releaseAlert` and `listParentEmails`, keeps `findOfflineDevices` and `claimAlert` (always `emailed_at` null) and gains `resolveReturned(now)`. Response `{ recorded, skipped }`. The route no longer needs `RESEND_*`. The old `emailed_at` column stays (applied migration), unused.
3. **Schedule** (`lib/digest/schedule.ts`, pure): `latestDuePeriod(family, now)` converts `now` to the family timezone with `Intl` (invalid timezone falls back to `UTC`), finds the latest send moment at or before now (daily: local `digest_hour:00` today or yesterday; weekly: the latest Monday at that hour) and returns `{ frequency, periodStart (local date), start, end (UTC instants) }` for the day or Monday to Sunday before it. Returns `null` if `family.created_at` is after the send moment. Only the latest period is considered: downtime is caught up by the next run, older periods are not sent.
4. **Claim before send** (as #18): `claimDigest(familyId, frequency, periodStart)` inserts ignoring conflicts; no row inserted means skip. Parents come from `listParentEmails` (Auth admin by `parents.user_id`). No parents keeps the claim and sends nothing. Every send failed (at least one recipient) or a build error releases the claim (delete that exact key) so the next 15-minute run retries; any success keeps it. The key includes `frequency`, so switching Daily and Weekly never collides.
5. **Content** (`lib/digest/content.ts`): per child of the family (service role, always filtered by the family's child ids): incidents = alerts of the child's devices with `incident_last_seen_at` inside the period, from that time to `resolved_at` or "still offline", shown in the family timezone; usage rows of the period paged with `.range()` in pages of 1000, at most 30 pages per child (over the cap is an error for that child, never a silent cut; see platform notes); total seconds, top 3 domains by seconds, and `computeFocusScore(entries, homeworkDomainsFor(...))` over the whole period using the child's homework settings from #16 (none chosen: "Focus score not available, choose homework sites in the dashboard"). A failing child shows "Usage unavailable" and the others still render. Plain text ending with the dashboard link `APP_URL/dashboard` and "An offline laptop is normal if it was switched off." Subject `Family Guardian: daily digest <local date>` or `weekly digest <start> to <end>`. Domains are already allowed by ADR 0005; nothing from the digest is stored.
6. **Endpoint** `POST /api/digest/send`: auth like the offline endpoint (constant-time compare, empty secret gives 500); `RESEND_API_KEY`, `ALERT_FROM_EMAIL` and the new `APP_URL` are required (500 before any claim). Reuses `createResendMailer`. Counts `{ sent, skipped, failed }`, logged as counts only. A failure listing families gives 500.
7. **Cron**: `call_send_digests()` mirrors `call_offline_alerts()` (Vault `app_url` and `alert_cron_secret`, 10 s timeout, warning when missing); `cron.schedule('send-digests', '*/15 * * * *', ...)` and the purge job are guarded for PGlite. Verified by hand on production after merge.
8. **Settings** (`lib/digest/settings.ts`, parent's RLS client): `saveDigestSettings({ frequency, hour, timezone })` validates (`daily` or `weekly`, integer 0 to 23, IANA timezone via `Intl.DateTimeFormat`), updates the caller's family with `.select("id")` (zero rows is `failed`) and sets `timezone_known = true`. `captureFamilyTimezone(tz)` updates the timezone only while `timezone_known` is false; a small client component on `/dashboard` calls it once per visit. Page `/dashboard/settings`: Daily or Weekly (Monday) radio, hour select 0 to 23, a note that all parents of the family receive the digest, and a nav link.
9. **Known limits.** Changes apply from the next run; a digest lost to a function timeout between claim and send is not retried; if one of two parents' sends fails that parent is not retried. A laptop switched off every evening still appears as an incident; the wording says that is normal.
